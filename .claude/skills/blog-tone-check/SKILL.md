# 말투 검사

이 저장소 글이 **사용자 문체**에 맞는지 점검한다. 규칙은 세 곳에 나뉘어 있고, 대상에 따라 적용 범위가 다르다. 대상을 먼저 분류하지 않으면 오탐이 난다.

## 0. 규칙 원본 확인

기억에 의존하지 말고 매번 읽는다. 세 곳이 서로 어긋나면 사용자에게 확인한다.

1. **전역 `~/.claude/CLAUDE.md`**: 게시 콘텐츠의 거짓, 과장, 단언 금지와 타사 IP 보호. **외부 공개 문서에만** 적용되는 항목이 있다.
2. **`docs/writing-style.md`**: 이 저장소 블로그 문체 정립본.
3. **프로젝트 메모리** `~/.claude/projects/-Users-kimenugi-workspace-dev-gnajournal-gnajournal-astro/memory/`
   - `blog-formal-tone` (금지 목록의 원본, 가장 상세)
   - `blog-writing-short-sentences` (문장 길이)
   - `blog-user-voice` (문체 표본, 노트와 블로그의 리듬 차이)
   - `markdown-bold-korean-gotcha` (굵게 함정)
   - `question-is-not-edit-request` (질문에는 답만, 수정은 지시가 있을 때만)

정립본(`docs/writing-style.md`)은 메모리의 정리본이다. 새 규칙이 메모리에만 들어와 있을 수 있으니 **양쪽을 다 본다.**

## 1. 대상 분류 (톤이 다르다)

| 대상 | 종결과 리듬 | 적용 규칙 |
|---|---|---|
| **블로그 게시글** (`src/content/blog/*.md`) | 존댓말(~합니다, ~됩니다). 핵심만 굵게 | 문체 규칙 전체 + 게시 콘텐츠 규칙 + 타사 IP |
| **학습용 문서, 비공개 노트, gist** | 명사형 종결("~하는 방식.", "~변경 가능") 허용, 이따금 느낌표 허용 | 문체 규칙 일부만. 과장과 타사명 규칙은 외부 공개가 아니면 완화 |
| **채팅 답변** | 존댓말 | 금지 문자만(em dash, 가운뎃점, 굵게 함정) |

**학습용 노트를 블로그 기준으로 지적하지 않는다.** 노트의 명사형 종결과 느낌표는 사용자의 정상 문체다. 블로그로 옮길 때 존댓말로 바꾸되 그 리듬(짧은 절, 핵심만 굵게, 예시 즉시 첨부)은 유지한다.

**외부 공개 여부**로 게시 콘텐츠 규칙 적용을 가른다. GitHub 공개 저장소, 페이지, PR과 이슈 본문, 블로그, SNS는 모두 "외부"다. 비공개 노트와 벤치마킹 메모는 "내부"라 타사 제품명 표기가 가능하다.

## 2. 기계 검출 (모든 대상 공통)

코드블록과 인라인 코드는 **삭제하지 말고 빈 줄로 치환**한다. 줄을 지우면 `grep -n`이 주는 번호가 원본과 어긋나 보고가 틀린다.

```bash
F=<검사할 파일>
S=$(awk '/^[[:space:]]*```/ { infence=!infence; print ""; next } infence { print ""; next } { print }' "$F" | sed 's/`[^`]*`//g')

echo "$S" | grep -nE '—' && echo "  ^ em dash 금지"
echo "$S" | grep -nE '·' && echo "  ^ 가운뎃점 나열 금지"
echo "$S" | grep -nE '\)\*\*[가-힣]' && echo "  ^ 굵게 함정: )** 뒤 한글은 렌더 안 됨"
```

블로그 게시글이면 아래까지 검사한다. 저장 시 `.claude/hooks/blog-style-check.sh`가 막는 항목이라 **필수 수정**이다.

```bash
echo "$S" | grep -nE '\*\*[^*]+\.\*\*' && echo "  ^ 굵은 라벨 뒤 마침표 → 콜론 형식"
echo "$S" | grep -nE '흥미로운 점은|놀랍게도|재미있는 건|재밌는 건' && echo "  ^ 필러 도입부"
echo "$S" | grep -nE '키잉|판별선|이름 집합' && echo "  ^ 압축 조어/음차"
echo "$S" | grep -nE '싣는|싣고|실린다|실리는|실리지' && echo "  ^ 운반 메타포"
echo "$S" | grep -nE '다른 축|두 축|남은 축|축입니다|축이다' && echo "  ^ 추상 메타포 명사(축)"
```

표기 검사는 코드를 지우면 안 되므로 **원본 파일 `$F`에 직접** 돌린다. (2026-08-14 추가.)

```bash
# 인라인 코드 뒤 조사는 붙여 쓴다. 띄우면 조사가 뒤 단어에 붙어 읽힌다.
# 예: `String?` 이 값과  ->  "이 값"으로 읽힘.  `null` 이 한쪽  ->  "이 한쪽"
grep -nE '`[^`]+` (이|가|은|는|을|를|와|과|의|에|로|도|만|입니다|이고|라는|처럼|부터|까지)([ ,.)\]]|$)' "$F" \
  && echo "  ^ 인라인 코드 뒤 조사는 붙여 쓸 것 (기존 글 전체가 붙임)"

# 눈에 안 보이는 non-breaking space. 편집이 어긋나고 하드 줄바꿈으로 렌더될 수 있다.
grep -nP '\xc2\xa0' "$F" && echo "  ^ non-breaking space를 일반 공백으로"

# 행말 공백 두 개는 마크다운 하드 줄바꿈이 된다. 이 블로그는 문단 단위로만 끊는다.
grep -nE '[ \t]+$' "$F" && echo "  ^ 행말 공백 제거"
```

## 3. 판단 항목 (문맥을 읽고 결정)

grep으로 후보만 뽑고, 진짜 위반인지는 문맥을 읽어 판단한다. 기계적으로 전부 고치지 않는다.

```bash
echo "$S" | grep -nE '다음과 같습니다|먼저 .{0,10}(정의|짚|살펴)|한 가지 더|핵심 전제는|정리하면|짚어야 할|만합니다|여기서.{0,8}있습니다|정리해 둘|정리해 두면|짚고 넘어|살펴보겠|주의할 점이 있|알아둘 점|이런 셈입니다|규칙은 이렇습니다' # 신호등, 필러(예고만 하고 사실로 안 들어가는 문장)
echo "$S" | grep -nE '직접 밝히|고 적었습니다|고 말했습니다|원문을 그대로|라고 지적했습니다' # 인용 귀속
echo "$S" | grep -nE '오해가 있습니다|흔한 오해' # 오해 프레임
echo "$S" | grep -nE '명확한|확실한' # 검증 안 되는 수식어
echo "$S" | grep -nE '^#{2,4} .*[.]$' # 제목 끝 마침표
echo "$S" | grep -nE '추측이 아니|분명히|사실 [^가-힣]|말 그대로' # 방어적 호소, 과잉 강조
echo "$S" | grep -nE '날리|터진|터졌|진가|손을 대|맞물리' # 비유적 표현 후보
echo "$S" | grep -nE '거든요|겠죠|이죠|하죠|하면 됩니다만|박아 넣|박지 않|직접 박|박는' # 구어체, 박다 계열
echo "$S" | grep -nE '다른 공간|두 공간|긴장|상수입니다|상수다' # 추상 메타포 명사(축 외)
echo "$S" | grep -nE '부분 종속|함수 종속[^적]' # 약식 용어(정식은 부분 함수적 종속, 함수적 종속)
echo "$S" | grep -vE '^\s*[-*|>#]' | awk 'length($0)>120 {print NR": "substr($0,1,90)}' # 긴 문장 후보
```

grep으로 못 잡는 것은 읽으면서 본다.
- **전문 용어 뜻 병기**: 스텁, ITPM, JSONL 같은 용어가 **첫 등장에서** 괄호나 짧은 문장으로 정의됐는지. 정의 없이 등장하면 위반.
- **방법 문단의 첫 문장**: 방법을 제시하는 문단이 "~해야 합니다"로 할 일을 먼저 밝히는지. 서술형이면 지시인지 상태 설명인지 갈린다.
- **지시어의 대상**: "그 파일", "이 값" 같은 지시어가 직전의 다른 명사로 오해될 수 있으면 대상을 다시 쓴다.
- **용어 표기 일관성**: 같은 글, 같은 시리즈에서 한 개념을 두 표기로 쓰지 않았는지.

판단 기준:
- **신호등(메타 스캐폴딩)**: 내용을 예고만 하고 사실로 안 들어가는 문장은 뺀다.
- **인용 귀속**: 따옴표에 저자나 논문을 붙이면 독자는 축자 인용으로 읽는다. 1차 출처로 대조했을 때만 그렇게 쓴다. 못 했으면 따옴표를 빼고 요지만 쓰거나 의역임을 드러낸다. **논리적으로 꼭 증명해야 할 때만 남기고** 나머지는 끝의 참고 문헌으로.
- **조어**: 표준이 아닌데 정식 용어처럼 쓴 말, 압축 명사구, 새로 정의해 쓰는 단어. 통용되는 담백한 표현으로.
- **번역투**: 이중 목적격("~를 ~를"), 영어 음차, 관용구로 상황을 요약하는 문장. 느낀 바를 직접 말한다.
- **비유적 표현**: "쿼리를 날리다", "터지다", "진가가 드러나다"를 직설적 용어로("쿼리를 실행하다", "오류가 발생하다").
- **구어체**: "흔한 오해 하나", "~하면 됩니다만" 같은 표현을 문어체로.
- **방어적 호소, 과잉 강조**: "이는 추측이 아니라 소스에 드러나 있습니다", "분명히", "사실 ~다"는 비굴하게 들린다. 빼고 근거 위치만 담백하게.
- **공식 용어 통일**: 약식 대신 정식 용어("부분 종속" 대신 "부분 함수적 종속"). 같은 시리즈 안에서 표기를 일관되게.
- **추상 메타포 명사**: 축, 공간, 긴장, 상수로 개념을 부르지 않고 가리키는 대상을 그대로 말한다.
- **제목 문법**: 마침표 금지, 물음표는 질문형만, 메타 서수 금지, 극적이거나 자화자찬인 단어 금지. 명제형, 명사구형, 짧은 질문형, 이유 구절형 중 하나. 질문형이면 본문 첫 문단이 바로 답하는지 확인.
- **문장 길이**: 한 문장에 절이 여러 개면 마침표로 나눈다. 한 문장은 한 생각.
- **문체 표본과의 결**: 격식어보다 일상어, 결론을 앞에, 숫자와 관찰로 말하기, 1인칭 주어 생략.
- **도입부 서사 (게시글의 사건 회고 도입부만)**: 인물부터 등장해 정보를 압축 나열하는 중립 3인칭 보고체면 위반. 네 가지를 확인한다. (1) 무대를 내 것으로 먼저 깔았는지(인물부터가 아니라 "제가 만든 ~"), (2) 상황→갈등→인물→행동→결과→문제 순서인지, (3) 행위자와 '선택'을 명시했는지(무주어 "바꾸자"로 안 흐렸는지), (4) 도입부에서 갈등을 완성했는지(인용에서 멈추지 않고 판단이 규칙으로 굳어진 것까지). 원본: `docs/writing-style.md` §8, 메모리 `blog-user-voice`.
- **섹션 간 전개**: 앞 섹션이 A(왜 느렸나)로 끝났는데 다음 섹션 제목이 B(빨라진 이유)로 시작하면, 그 사이를 잇는 문장이 있는지. 다음 제목의 핵심어가 받을 대상이 앞 섹션 끝에 없으면 갑작스럽다.
- **주장 확신 수위 일관성**: 한 곳에서 "측정 없이는 알 수 없다"고 신중하게 말하고 다른 곳에서 "X가 원인이었다"로 단정하면 충돌이다. 가장 강한 결론("적어도 X를 원인으로 지목할 근거는 없었다")까지만.
- **실험 범위 한정**: 특정 조건(값 5만, 특정 버전) 결과를 다른 조건(작은 리스트, 실제 사건)에 그대로 옮기지 않았는지. "이 실험에서는", "크기가 달랐으므로 같다고 볼 수 없다"로 한정했는지.
- **관측과 단정 구분** (2026-08-05 추가): 관측한 것을 확정 사실로 단정하지 않았는지. "Gradle import가 시작됐습니다"(단정)가 아니라 "No applicable build tools 메시지가 사라지고 모듈을 읽는 로그로 이어졌습니다"(관측). 행위 주체를 정확히 귀속했는지(루트를 고르는 건 언어 서버가 아니라 클라이언트). 미검증 기능은 "동작한다"가 아니라 "확인 중" 또는 "자기 환경에서 확인"으로. 사실 명제에는 출처를 다는지. 원본: `docs/writing-style.md` §8.
- **재지칭**: 인물이 비인칭 섹션을 지나 다시 나올 때 대명사("그가")로만 받지 않고 역할("이 기능을 맡은 분이")로 재지칭했는지.
- **제목 범위**: 두 절을 쉼표로 이은 문장형 제목이거나, 본문보다 큰 범위를 약속하는 제목이 아닌지.

## 4. 게시 콘텐츠 전용 검사 (외부 공개 문서만)

전역 `~/.claude/CLAUDE.md`의 규칙이다. 내부 노트에는 적용하지 않는다.

```bash
echo "$S" | grep -nE '최고의|최강의|압도적|유일한|완벽|반드시|확실히|100%|절대|마스터|정복|전문가가 되|프로 수준|달인'
```

**과장은 구절 전체가 아니라 요소별로 판단한다.**
- 하나라도 있으면 금지: 도달 수준 약속(마스터, 정복, 전문가가 되세요), 우월성(최고의, 압도적, 유일한), 절대 기준(완벽), 보장(반드시, 100%, 절대)
- 모든 요소가 사실이면 허용: 시간("5초만에"), 톤("쉽게"), 범위("완전 가이드"), 즉시성("바로"), 단계("차근차근")
- 예: "5초만에 쉽게"는 허용, "5분만에 전문가"는 금지(전문가 = 결과 보장)

그 밖에 확인할 것:
- **미검증 서술**: 검증 못 한 기능을 "현재 작동"으로 적지 않았는지. 못 했으면 미래형(예정, 계획)으로.
- **수치와 인용**: 출처를 확인하고 썼는지. 서지정보가 없으면 빼고 실무 트레이드오프로 서술.
- **타사 제품명**: 상표나 제품명 직접 언급, 호환성이나 제휴 단언이 없는지. 일반화 표현으로 바꾼다.

## 5. 보고

찾은 것만 간결하게 보고한다. 항목마다 줄 번호, 원문 인용, 걸리는 규칙, 고친 문장 제안을 붙인다.

**필수 수정(훅 차단)과 판단 항목을 나눠서** 보고해 무엇이 반드시 고쳐야 할 것인지 드러낸다. 대상 분류 결과(블로그인지 노트인지)도 함께 밝혀, 어떤 규칙을 적용했는지 알 수 있게 한다. 위반이 없으면 "위반 없음"이라고 명시한다.

## 6. 수정

**사용자가 고치라고 했을 때만 고친다.** 질문이나 검토 요청은 보고까지다(`question-is-not-edit-request`).

- **원문에 없던 내용을 새로 만들지 않는다.** 문장을 다듬는 것이지 사실을 보태는 것이 아니다. 없던 주장이나 수치, 예시를 채워 넣으면 검증 안 된 서술이 되어 게시 콘텐츠 규칙까지 어긴다.
- **비유적 표현을 새로 만들지 않는다.** 고치면서 비유나 관용구를 끌어들이지 말고, 실제 동작과 상태를 그대로 적는다.
- 뜻을 바꾸지 않는 **최소 수정**을 기본으로 한다. 지울 수 있으면 바꾸기보다 지운다.
- 굵은 라벨 마침표 같은 기계적 변환은 한 번에 처리한다.
- 인용 삭제나 문단 재작성처럼 뜻이 달라지는 수정은 제안을 보이고 확인받는다.
- 수정 후 2단계 검사를 다시 돌려 훅에 걸릴 것이 없는지 확인한다.

## 원칙
- 설명을 더 하는 이유는 **쉽게 읽히게 하려는 것**이다. 읽는 데 부담이 될 만큼 많이 적으면 목적에 어긋난다.
- 존댓말 종결은 블로그에서 정상이고, 명사형 종결은 노트에서 정상이다. 둘 다 지적하지 않는다.
- 관용 기술용어(fetch join, semijoin 등)는 한글 설명을 병기하면 허용한다.
- 새 규칙이 정해지면 `docs/writing-style.md`와 메모리(`blog-formal-tone`)에 **함께** 반영한다.
