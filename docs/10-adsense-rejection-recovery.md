# 애드센스 "가치가 별로 없는 콘텐츠" 거절 대응

meeemo.net이 2026년 8월 18일에 이 사유로 거절당한 뒤, 원인을 조사하고 고친 기록이다.
다른 사이트를 신청할 때 재사용할 수 있도록 체크리스트를 함께 정리했다.

설정 방법 자체는 [04-adsense-setup.md](./04-adsense-setup.md)를 본다. 이 문서는 거절
이후의 대응만 다룬다.

---

## 1. 상황

| 항목 | 값 |
|---|---|
| 사이트 | meeemo.net |
| 판정 | 주의 필요, "가치가 별로 없는 콘텐츠" |
| 통보일 | 2026년 8월 18일 |
| ads.txt 상태 | 승인됨 |
| 같은 계정의 다른 사이트 | snaprhythm.net 준비됨(승인), chessmotifstats.com 같은 사유로 거절 |

같은 계정의 snaprhythm.net이 승인 상태였다. 계정 문제가 아니라 **사이트 단위 심사에서
걸린 것**이다.

---

## 2. 조사에서 확인한 사실

구글은 어느 항목에서 몇 점을 깎았는지 알려주지 않는다. 아래는 관측으로 확인한 것과
추정을 구분해서 적는다.

### 2-1. 색인의 절반 이상이 얇은 태그 페이지였다 (확인됨)

서치콘솔 페이지 색인 생성 보고서 기준이다.

| 항목 | 값 |
|---|---|
| 색인 생성됨 | 45개 |
| 색인 생성되지 않음 | 11개 |
| 라이브 sitemap URL | 19개 |

**색인 45개인데 sitemap은 19개다. 차이 26개는 sitemap에 없는 페이지가 색인됐다는 뜻이다.**

색인 목록 상위 10개를 직접 확인한 결과다.

```
https://meeemo.net/                          2026. 8. 14.
https://meeemo.net/tags/Kotlin/              2026. 8. 4.
https://meeemo.net/tags/함수적종속성/          2026. 8. 4.
https://meeemo.net/blog/claude-code-prompt-caching/
https://meeemo.net/blog/jpa-orphan-removal-unique-key/
https://meeemo.net/blog/in-vs-exists-mysql-mariadb/
https://meeemo.net/tags/유니크키/             2026. 8. 4.
https://meeemo.net/tags/H2/                  2026. 8. 4.
https://meeemo.net/tags/flush/               2026. 8. 1.
https://meeemo.net/tags/비용/                 2026. 8. 1.
```

10개 중 6개가 태그 아카이브였다. `flush`, `비용`, `H2`, `유니크키`, `함수적종속성`은
**글이 1편뿐인 태그**다. 제목 하나와 요약 한 줄만 있는 페이지다. 사이트가 빌드하는 태그
페이지는 총 40개였다.

심사 시점에 구글이 본 사이트는 대략 이런 구성이었다.

- 실제 기술글 14편
- 홈, 소개, 개인정보처리방침 등 유틸 페이지 5개
- 거의 비어 있는 자동 생성 아카이브 약 26개

### 2-2. 고쳐놨는데 구글이 못 봤다 (확인됨)

태그 페이지에는 이미 noindex가 걸려 있었다.

```
$ curl -s https://meeemo.net/tags/flush/ | grep robots
<meta name="robots" content="noindex, follow">
```

문제는 순서였다.

| 시점 | 일 |
|---|---|
| 8월 1일 ~ 4일 | 구글이 태그 페이지를 마지막으로 크롤링 |
| 8월 9일 | noindex 배포 |
| 8월 18일 | 거절 통보 |

**noindex를 붙인 뒤로 구글이 그 페이지들을 다시 방문하지 않았다.** 그래서 색인에 그대로
남았고, 심사도 고치기 전 상태로 받았다.

이 문서에서 가장 중요한 교훈이다.

> noindex를 걸어도 구글이 재크롤링하기 전에는 색인에서 빠지지 않는다.
> 고친 직후에 신청하면 고치기 전 상태로 심사받는다.

### 2-3. 소개 페이지가 템플릿 문구였다 (확인됨)

Astro 템플릿의 문구가 그대로 남아 있었다.

- "개인적인 이야기와 기술적인 내용을 함께 기록하는 공간입니다" (실제 공개 글 14편은 전부 기술글)
- "일상: 일상적인 이야기와 생각" (해당 글 0편)
- "기록: 읽은 책, 본 영화" (해당 글 0편)
- "각 글의 댓글로 남겨주세요" (**댓글 기능이 동작하지 않음**)

댓글 항목은 명백한 거짓이었다. Giscus 컴포넌트가 플레이스홀더 상태였다.

```js
const repo = 'YOUR_GITHUB_USERNAME/YOUR_REPO_NAME';
if (repo === 'YOUR_GITHUB_USERNAME/YOUR_REPO_NAME') return;
```

미설정 안내 문구는 `import.meta.env.DEV` 조건이라 프로덕션에서는 보이지 않았다. 결과적으로
라이브 글 페이지에는 빈 div만 있고 댓글창이 없는데, 소개 페이지는 댓글로 연락하라고
안내하고 있었다.

### 2-4. 크롤러 접근은 정상이었다 (확인됨)

"사이트 다운"이 거절 사유가 되기도 한다길래 확인했으나 문제가 없었다.

```
Googlebot:            HTTP 200
Mediapartners-Google: HTTP 200
AdsBot-Google:        HTTP 200
```

robots.txt도 정상이었다. `User-agent: *`에 `Allow: /`가 있고, 차단은 AI 학습 크롤러
(GPTBot, ClaudeBot, Google-Extended 등)만 걸려 있었다. Google-Extended 차단은 Gemini
학습만 막을 뿐 검색이나 애드센스와 무관하다.

### 2-5. 확인하지 못한 것

- 구글이 실제로 어느 항목을 문제 삼았는지
- 공개 글 14편이라는 분량이 단독으로 거절 사유가 되는지

분량 기준은 공식 문서에 없다. 아래 후기 사례는 참고일 뿐이다.

### 2-6. 기술 감사 전 항목 통과 (확인됨, 2026-08-19)

`adsense-approval` 스킬의 감사 스크립트를 돌린 결과다.

| 섹션 | 결과 |
|---|---|
| 0. 간헐적 5xx (40회 순차) | **실패 0/40** |
| 1. 광고 코드가 서버 HTML에 | 실제 `<script>` 태그 1개, preload 0개 |
| 2. ads.txt | 200 `text/plain`, www와 http 변형 정상, 크롤러 3종 200 |
| 4. robots.txt 충돌 | `User-agent: *` 블록에 Disallow 없음 |
| 5. 리다이렉트 | 308 (307 아님) |
| 6. canonical | 가리키는 URL이 200 |

**5xx는 원인이 아니다.** 이 스킬이 만들어진 원 사례에서는 간헐적 503이 진짜 원인이었으므로
먼저 확인했으나, meeemo.net은 40회 연속 요청에 실패가 없었다. Cloudflare Pages 정적
호스팅이라 Worker CPU 한도(에러 1102)를 칠 경로도 없다.

깨진 내부 링크도 전수 검사했다. 69개 페이지, 내부 링크 참조 1,692건에서
**깨진 링크 0건**이다. 글 0개인 카테고리나 태그 페이지도 없다.

### 2-7. 새로 나온 결함: robots.txt에 사이트맵이 없다 (확인됨)

```
/sitemap.xml        404
/sitemap-index.xml  200
robots.txt의 Sitemap 지시자: 없음
```

Cloudflare가 관리형 robots.txt를 대신 내주고 있어서(AI 학습 크롤러 차단 목록이 든 그 파일)
우리 사이트맵 경로가 적혀 있지 않다. 관행적 경로인 `/sitemap.xml`도 404다. Astro의 sitemap
통합은 `sitemap-index.xml`을 만든다.

색인 45개가 잡힌 것을 보면 서치콘솔에 사이트맵이 제출돼 있어 당장 치명적이지는 않다.
다만 `public/robots.txt`를 만들어 덮어쓸 경우 **Cloudflare 관리형 파일의 AI 크롤러 차단
목록을 우리 파일에 그대로 옮겨 적어야 한다.** 그냥 덮어쓰면 그 차단이 사라진다.

### 2-8. 글의 실증 강도 측정 (확인됨)

"우리 글에 우리 경험이 없는가"를 재봤다. 공개 글 14편 전수다.

| 글 | 코드블록 | 1인칭 검증 서술 | 인용 |
|---|---|---|---|
| in-vs-exists | 5 | **20** | 6 |
| kotlin-lsp | 13 | **17** | 8 |
| prompt-caching | 4 | 8 | 38 |
| api-null-put-patch | 13 | 5 | 42 |
| jpa-orphan-removal | 13 | 5 | 11 |
| spring-test-oom | 7 | 5 | 6 |
| linear-referencing | 0 | 3 | 2 |
| jpa-n-plus-one | 7 | 0 | 0 |
| **정규화 1~6편 합계** | **1** | **1** | **58** |

- 본문 글자수: 최소 4,548, 중앙값 8,134, 최대 24,504
- **소제목 조합이 완전히 겹치는 글 묶음 0개.** 템플릿으로 찍어낸 사이트가 아니다
- 14편 중 10편에 시각자료가 있다

**정규화 시리즈 6편이 약하다.** 6편을 통틀어 코드블록 1개, 1인칭 검증 서술 1회인데 인용은
58회다. 출처는 잘 달려 있으나 이 사이트만 만들 수 있는 데이터가 없다. 그리고 이 6편이
공개 글의 43%다.

**지표의 한계를 밝힌다.** 이건 키워드 세기라 서술 방식을 잴 뿐 경험의 유무를 직접 재지
못한다. `linear-referencing` 글은 1인칭 서술이 3회뿐이지만 QGIS 실제 작업 이미지가 6장
들어 있다. 키워드로 안 잡히는 실증이다. 반대로 정규화 시리즈는 세 지표가 모두 같은 방향을
가리켜서 판단에 무게가 실린다.

### 2-9. 독창성 자가진단 (확인됨)

정규화 시리즈에서 특징적인 문장을 뽑아 검색했다.

- 결과: **문장 단위 복제는 없다.** 표현은 독창적이다
- 그러나 **같은 주제를 같은 직원/부서 예시로 다룬 국내 블로그가 다수 검색된다**
  (velog, tistory, github.io 등)

즉 표절은 아니지만 차별점이 없다. 반려 사유 1번이 말하는 "독자가 이 글에서만 얻을 수 있는
게 없다"에 정확히 해당한다. 반대로 강한 글들(EXISTS 통념 검증, Kotlin LSP의 Gradle 루트
문제, Hibernate flush 순서와 유니크키)은 검색에서 같은 내용을 찾기 어려운 주제다.

## 2-A. 반려 사유 6가지와 우리 사이트 대조

애드센스 반려 사유는 여섯 가지로 나뉜다. 각각에 대해 현재 상태를 적는다.

| 사유 | 정의 | meeemo.net (2026-08-19) |
|---|---|---|
| 1. 가치가 별로 없는 콘텐츠 | 독자가 이 글에서만 얻을 것이 없음 | **받은 판정.** 14편 중 6편(정규화)이 여기 해당 |
| 2. 콘텐츠 없음 또는 불충분 | 글이 적거나 한 편 분량 부족 | 분량은 통과(중앙값 8,134자). **개수 14편으로 미달** |
| 3. 사이트 이용 불가 | 심사 로봇이 접속 실패 | 배제됨. 5xx 0/40, 크롤러 3종 200 |
| 4. 탐색이 어려운 사이트 | 메뉴 구조와 기본 페이지 부재 | 2026-08-18에 해소. 소개, 연락처, 개인정보처리방침, 카테고리, 깨진 링크 0 |
| 5. 정책 위반 | 저작권 침해, 복제 페이지 등 | 문장 복제 없음 확인. **이미지 출처는 미점검** |
| 6. 사유 없는 반려 | 사유 미통보 | 해당 없음. 우리는 사유를 받았다 |

**1번과 2번만 남았고, 둘 다 같은 곳을 가리킨다.**

## 3. 다른 사이트에 쓸 체크리스트

### A. 색인 위생 (이번 사례의 핵심)

- [ ] 서치콘솔에서 **색인 생성됨 개수와 sitemap URL 개수를 비교**한다. 색인이 더 많으면 무엇이 추가로 색인됐는지 목록을 연다.
- [ ] 글이 1~2편뿐인 자동 생성 아카이브(태그, 연도, 작성자, 페이지네이션)가 색인되고 있는지 본다.
- [ ] 얇은 아카이브는 `noindex`와 sitemap 제외를 함께 건다. 둘 중 하나만 하면 부족하다.
- [ ] noindex 배포 뒤 **서치콘솔에서 해당 URL의 마지막 크롤링 날짜**를 확인한다. 배포일보다 이전이면 아직 반영되지 않은 것이다.
- [ ] 색인 숫자가 의도한 값으로 내려간 뒤에 신청한다.

**이미 색인된 페이지에 noindex를 붙인 경우, 재크롤링을 앞당길 직접적인 수단이 없다.**
(2026-08-20 실측으로 확인.)

기대했던 방법과 실제 결과다.

| 방법 | 결과 |
|---|---|
| URL 검사에서 개별 색인 요청 | **불가.** 요청이 거부된다 |
| 사이트맵으로 유도 | 얇은 아카이브는 이미 sitemap에서 뺐으므로 걸리지 않는다 |
| 삭제 도구 | 가능하지만 임시(6개월) 조치다. 아래 "하지 말 것" 참고 |
| 자연 재크롤링 | 유일한 정공법. 시점을 통제할 수 없다 |

**왜 색인 요청이 거부되는가.** 서치콘솔은 요청을 크롤링 대기열에 넣기 전에 **실시간
테스트**를 먼저 돌린다. 지금 이 순간 그 URL을 실제로 가져와 색인 가능한 상태인지 보는
절차다. 거기서 `noindex`를 발견하면 색인될 수 없는 페이지로 판정하고 요청 자체를 막는다.

```
색인 생성 요청이 거부됨
실시간 테스트 중에 URL에서 색인 생성 문제가 감지되었습니다.
```

"색인해 달라고 요청해서 구글을 불러온 뒤, 와서 noindex를 보고 알아서 빼게 한다"는
우회를 쓸 수 없다는 뜻이다. **구글이 정식으로 크롤링하러 오기 전에 실시간 테스트
단계에서 막힌다.** 참고로 이 메시지는 사이트 결함 신고가 아니다. `noindex`는 우리가
의도적으로 붙인 것이고, 구글은 요청과 페이지 설정이 어긋난다고 알려준 것뿐이다.

**그래서 순서를 바꾼다.** 얇은 아카이브에는 **색인되기 전에** noindex를 건다. 이미
색인된 뒤라면 되돌리는 데 시간이 얼마나 걸릴지 통제할 수 없다. 이 사례에서는 noindex
배포 11일 뒤에도 재크롤링이 일어나지 않았다.

**간접적으로 할 수 있는 것.** 사이트맵을 재제출하고, 아직 크롤링되지 않은 정상 페이지에
색인을 요청한다. 구글봇이 그 페이지들을 가지러 사이트에 오면 다른 페이지도 함께 훑을
가능성이 있다. 다만 이건 확인된 인과가 아니라 기대다.

### B. 사이트 정합성

- [ ] 소개(About) 페이지가 실제 콘텐츠와 일치하는가. **템플릿 기본 문구가 남아 있지 않은가.**
- [ ] 없는 기능을 안내하고 있지 않은가 (댓글, 문의 양식, 뉴스레터, 검색)
- [ ] 홈의 사이트 설명과 소개 페이지의 주제 서술이 서로 어긋나지 않는가
- [ ] 플레이스홀더가 남아 있지 않은가 (`G-XXXXXXXXXX`, `YOUR_REPO_ID`, `lorem ipsum`, `example.com`)
- [ ] "설정해주세요" 같은 제작 중 표시가 프로덕션에 노출되지 않는가

플레이스홀더는 아래 한 줄로 훑을 수 있다.

```bash
grep -rniE 'YOUR_|XXXXX|lorem ipsum|example\.com|TODO' dist/ | grep -v '\.js:'
```

### C. 탐색 구조

- [ ] 카테고리가 있는가. 태그만으로는 주제 구조가 드러나지 않는다.
- [ ] **각 카테고리에 글이 3편 이상 있는가.** 1편짜리 카테고리는 얇은 태그 페이지를 반복하는 것이다.
- [ ] 카테고리 페이지에 목록 말고 **소개 문단**이 있는가. 목록만 있으면 그것도 얇은 페이지다.
- [ ] 브레드크럼과 BreadcrumbList 구조화 데이터가 있는가
- [ ] 헤더 메뉴만 봐도 사이트 주제가 보이는가

### D. 신뢰 요소

- [ ] 개인정보처리방침 (애드센스 필수)
- [ ] 문의 페이지. **실제로 동작하는 연락 수단만** 적는다. 정적 사이트면 양식 대신 이메일을 쓰고, 양식이 없는 이유를 밝힌다.
- [ ] 운영자 정보가 글 페이지에서도 보이는가 (바이라인, 하단 소개 박스)
- [ ] Article 또는 BlogPosting 구조화 데이터에 author와 publisher가 있는가
- [ ] 운영자 이름이 페이지마다 다르지 않은가 (단일 출처로 관리)

### E. 접근성

- [ ] 구글 크롤러 세 종류로 200이 나오는가

```bash
curl -s -o /dev/null -w "%{http_code}\n" -A "Googlebot" https://example.com/
curl -s -o /dev/null -w "%{http_code}\n" -A "Mediapartners-Google" https://example.com/
curl -s -o /dev/null -w "%{http_code}\n" -A "AdsBot-Google" https://example.com/
```

- [ ] robots.txt에서 위 셋이 차단되지 않았는가
- [ ] ads.txt에 실제 게시자 ID가 들어갔는가
- [ ] www와 apex가 모두 응답하고, canonical이 한쪽을 가리키는가

### F. 콘텐츠

- [ ] 글이 몇 편인가. 공식 기준은 없다. 아래 후기 사례가 참고가 된다.
- [ ] AI로 대량 생성한 글이 섞여 있지 않은가. 거절 사유로 가장 많이 지목된다.
- [ ] 한 주제를 여러 편으로 쪼갠 시리즈가 전체의 절반을 넘지 않는가. 목록만 보면 비슷한 글의 반복으로 보인다.

## 3-A. 검사 방법이 틀리는 방식

"확인했다"와 "확인한 방법이 옳았다"는 다르다. 이 작업에서 실제로 겪은 것들이다.

**더 큰 집합을 검색해서 오판한다.** 깨진 링크 검사기가 `href="..."` 를 원시 HTML에서
전부 긁었더니, 검색 페이지의 클라이언트 스크립트 안 템플릿 문자열
`href="/blog/${post.id}/"` 이 깨진 링크로 잡혔다. 런타임에 채워지는 정상 코드다.
CSS 파일도 확장자 목록 누락으로 오탐이 났다. **2건 모두 오탐이었다.**
찾으려는 것의 형태로 검색하고, 걸린 것을 하나씩 실제로 확인해야 한다.

**키워드 세기를 실체 측정으로 착각한다.** 1인칭 서술 횟수로 실증 강도를 쟀는데,
`linear-referencing` 글은 그 수치가 낮지만 QGIS 실제 작업 이미지가 6장 있다. 지표가
서술 방식만 재고 있었다. **여러 지표가 같은 방향을 가리킬 때만 판단에 무게를 싣는다.**

**남이 준 진단을 검증 없이 받는다.** "Worker CPU 한도 초과"라는 주석이 달린 503 로그를
받았으나, 40회 순차 요청에서 실패 0건이었고 사이트는 Worker를 쓰지 않는 정적 호스팅이었다.
에러 코드의 의미가 맞더라도 그것이 이 사이트에 적용되는지는 별개다.

**해보지 않은 절차를 문서에 적는다.** 이 문서 자체가 그랬다. "URL 검사에서 개별 색인
요청을 하면 구글이 다시 와서 noindex 를 보고 뺀다" 고 적어 두었는데, 2026-08-20 에 실제로
눌러 보니 요청이 거부됐다. 논리가 그럴듯해서 검증 없이 적은 것이다. **절차를 문서에 적을
때는 한 번은 실행해 보고 적는다.** 실행해 보지 않았으면 "해 보지 않음" 이라고 함께 적는다.

- 후기 중에서는 **본인 사례와 수치를 밝힌 글**만 참고할 값이 있다.
- "필승 공식", "승인 대행" 류는 근거 없는 수치를 단언한다. 특히 글자 수 제한은 긴 글이 강점인 사이트에 해롭다.

const uncategorized = posts.filter((post) => !post.data.category);
if (uncategorized.length > 0) {

## 5-A. 권고를 바꾼다

처음에는 **글 수를 늘리는 것**을 우선으로 제시했다. 지금은 **기존 정규화 6편을 실증으로
보강하는 것**을 우선으로 바꾼다. 무엇이 바뀌었는지(사실)와 무엇이 틀렸는지(추론)를 나눠 적는다.

**새로 확보한 사실**

- 정규화 6편의 코드블록 합계 1개, 1인칭 검증 서술 합계 1회 (2-8 측정)
- 같은 주제를 같은 예시로 다룬 국내 블로그가 다수 존재 (2-9 검색)
- 기술 항목은 전부 통과 (2-6 감사)

**틀렸던 추론**

"14편은 적으니 개수를 늘리면 된다"고 봤다. 개수가 미달인 것은 맞지만 **개수만 늘리면 약한
6편은 그대로 남는다.** 받은 판정이 "콘텐츠 없음"이 아니라 "가치가 별로 없는 콘텐츠"라는
점을 충분히 무겁게 보지 않았다.

**바뀐 권고**

1. 정규화 6편에 실증을 넣는다. 이상현상을 실제 테이블로 재현한 SQL과 실행 결과, 실행 계획,
   실무에서 겪은 설계 실패 같은 것이다. 이 사이트만 만들 수 있는 데이터가 목표다.
2. 그다음에 초안 중 실증이 있는 글을 게시해 개수를 올린다. 급조로 개수를 채우는 것은
   금지 항목이다.

## 6. 아직 하지 않은 것

- **태그 페이지 색인 제거는 기다리는 것 외에 수단이 없다.** 색인 요청은 거부되고(3-A 참고),
  사이트맵에는 이미 없다. 2026-08-20에 사이트맵 재제출과 정상 페이지 3건 색인 요청을 넣어
  구글봇을 부르는 것까지 했다. 색인 45개가 움직이는지 지켜본다.
- **정규화 6편 실증 보강 (1/6 완료).** 5-A 참고. 2편(이상현상)을 시범으로 보강했다.
  MariaDB 11.4.2에서 세 이상현상을 실제로 실행하고 출력을 옮겼다. 6,441자에서
  9,640자, 코드블록 0개에서 11개가 됐다. 나머지 5편이 남았다.

  시범에서 얻은 방법: **설명을 반복하지 말고, 실행해야만 알 수 있는 것을 찾는다.**
  이 글에서는 "세 이상현상 중 데이터베이스가 막아주는 것은 삽입 이상 하나뿐이고
  나머지 둘은 에러 없이 통과한다"가 그것이었다. 표로 설명할 때는 보이지 않던
  구분이다.
- **글 수 늘리기.** kmong 기준 15~25편에 14편으로 미달이다. 태그 26개가 색인에서 빠지면
  색인도 19개로 줄어든다. 초안 중 실증이 있는 것을 게시한다. 다만 위 항목보다 뒤다.
- **robots.txt에 Sitemap 지시자 추가.** 2-7 참고. Cloudflare 관리형 파일을 덮어쓰는
  것이므로 AI 크롤러 차단 목록을 옮겨 적을지 판단이 필요하다.
- **이미지 출처 점검.** 반려 사유 5번 항목인데 아직 확인하지 않았다.
- **애널리틱스 활성화.** GA4와 Cloudflare Analytics 둘 다 주석 처리 상태라 트래픽을 확인할
  수단이 없다. 재신청 판단 근거가 없다는 뜻이다.
- **Giscus 설정.** 지금은 소개 페이지에서 댓글 언급만 뺀 상태다. 실제로 붙이면 문장을
  되살린다.
- **이용약관과 면책고지.** 애드센스 필수 요건은 개인정보처리방침이다. 광고를 붙이는 사이트에
  있으면 좋다는 의견이 있어 판단이 필요하다.
해결됨(2026-08-18): `claude-code-kotlin-lsp-gradle-subdirectory` 글이 라이브에는 있는데
git에 없었다. 배포 직전에 발견해 커밋했다. 그대로 배포했으면 구글에 색인된 URL이 404가
될 뻔했다. **배포 전에 라이브 sitemap과 새 빌드 sitemap을 비교해 사라지는 URL이 없는지
확인하는 습관이 필요하다.**

```bash
curl -s https://example.com/sitemap-0.xml | grep -o '<loc>[^<]*' | sed 's/<loc>//' | sort > /tmp/live.txt
grep -o '<loc>[^<]*' dist/sitemap-0.xml | sed 's/<loc>//' | sort > /tmp/new.txt
comm -23 /tmp/live.txt /tmp/new.txt   # 출력이 있으면 그 URL이 사라진다
```
