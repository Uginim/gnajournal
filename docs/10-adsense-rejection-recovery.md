# 애드센스 "가치가 별로 없는 콘텐츠" 거절 대응

meeemo.net이 2026년 8월 18일에 이 사유로 거절당한 뒤, 원인을 조사하고 고친 기록이다.
다른 사이트를 신청할 때 재사용할 수 있도록 체크리스트를 함께 정리했다.

설정 방법 자체는 [04-adsense-setup.md](./04-adsense-setup.md)를 본다. 이 문서는 거절
이후의 대응만 다룬다.

---

## 1. 상황

| 항목 | 값 |
|---|---|
| 사이트 | meeemo.net |
| 판정 | 주의 필요, "가치가 별로 없는 콘텐츠" |
| 통보일 | 2026년 8월 18일 |
| ads.txt 상태 | 승인됨 |
| 같은 계정의 다른 사이트 | snaprhythm.net 준비됨(승인), chessmotifstats.com 같은 사유로 거절 |

같은 계정의 snaprhythm.net이 승인 상태였다. 계정 문제가 아니라 **사이트 단위 심사에서
걸린 것**이다.

---

## 2. 조사에서 확인한 사실

구글은 어느 항목에서 몇 점을 깎았는지 알려주지 않는다. 아래는 관측으로 확인한 것과
추정을 구분해서 적는다.

### 2-1. 색인의 절반 이상이 얇은 태그 페이지였다 (확인됨)

서치콘솔 페이지 색인 생성 보고서 기준이다.

| 항목 | 값 |
|---|---|
| 색인 생성됨 | 45개 |
| 색인 생성되지 않음 | 11개 |
| 라이브 sitemap URL | 19개 |

**색인 45개인데 sitemap은 19개다. 차이 26개는 sitemap에 없는 페이지가 색인됐다는 뜻이다.**

색인 목록 상위 10개를 직접 확인한 결과다.

```
https://meeemo.net/                          2026. 8. 14.
https://meeemo.net/tags/Kotlin/              2026. 8. 4.
https://meeemo.net/tags/함수적종속성/          2026. 8. 4.
https://meeemo.net/blog/claude-code-prompt-caching/
https://meeemo.net/blog/jpa-orphan-removal-unique-key/
https://meeemo.net/blog/in-vs-exists-mysql-mariadb/
https://meeemo.net/tags/유니크키/             2026. 8. 4.
https://meeemo.net/tags/H2/                  2026. 8. 4.
https://meeemo.net/tags/flush/               2026. 8. 1.
https://meeemo.net/tags/비용/                 2026. 8. 1.
```

10개 중 6개가 태그 아카이브였다. `flush`, `비용`, `H2`, `유니크키`, `함수적종속성`은
**글이 1편뿐인 태그**다. 제목 하나와 요약 한 줄만 있는 페이지다. 사이트가 빌드하는 태그
페이지는 총 40개였다.

심사 시점에 구글이 본 사이트는 대략 이런 구성이었다.

- 실제 기술글 14편
- 홈, 소개, 개인정보처리방침 등 유틸 페이지 5개
- 거의 비어 있는 자동 생성 아카이브 약 26개

### 2-2. 고쳐놨는데 구글이 못 봤다 (확인됨)

태그 페이지에는 이미 noindex가 걸려 있었다.

```
$ curl -s https://meeemo.net/tags/flush/ | grep robots
<meta name="robots" content="noindex, follow">
```

문제는 순서였다.

| 시점 | 일 |
|---|---|
| 8월 1일 ~ 4일 | 구글이 태그 페이지를 마지막으로 크롤링 |
| 8월 9일 | noindex 배포 |
| 8월 18일 | 거절 통보 |

**noindex를 붙인 뒤로 구글이 그 페이지들을 다시 방문하지 않았다.** 그래서 색인에 그대로
남았고, 심사도 고치기 전 상태로 받았다.

이 문서에서 가장 중요한 교훈이다.

> noindex를 걸어도 구글이 재크롤링하기 전에는 색인에서 빠지지 않는다.
> 고친 직후에 신청하면 고치기 전 상태로 심사받는다.

### 2-3. 소개 페이지가 템플릿 문구였다 (확인됨)

Astro 템플릿의 문구가 그대로 남아 있었다.

- "개인적인 이야기와 기술적인 내용을 함께 기록하는 공간입니다" (실제 공개 글 14편은 전부 기술글)
- "일상: 일상적인 이야기와 생각" (해당 글 0편)
- "기록: 읽은 책, 본 영화" (해당 글 0편)
- "각 글의 댓글로 남겨주세요" (**댓글 기능이 동작하지 않음**)

댓글 항목은 명백한 거짓이었다. Giscus 컴포넌트가 플레이스홀더 상태였다.

```js
const repo = 'YOUR_GITHUB_USERNAME/YOUR_REPO_NAME';
if (repo === 'YOUR_GITHUB_USERNAME/YOUR_REPO_NAME') return;
```

미설정 안내 문구는 `import.meta.env.DEV` 조건이라 프로덕션에서는 보이지 않았다. 결과적으로
라이브 글 페이지에는 빈 div만 있고 댓글창이 없는데, 소개 페이지는 댓글로 연락하라고
안내하고 있었다.

### 2-4. 크롤러 접근은 정상이었다 (확인됨)

"사이트 다운"이 거절 사유가 되기도 한다길래 확인했으나 문제가 없었다.

```
Googlebot:            HTTP 200
Mediapartners-Google: HTTP 200
AdsBot-Google:        HTTP 200
```

robots.txt도 정상이었다. `User-agent: *`에 `Allow: /`가 있고, 차단은 AI 학습 크롤러
(GPTBot, ClaudeBot, Google-Extended 등)만 걸려 있었다. Google-Extended 차단은 Gemini
학습만 막을 뿐 검색이나 애드센스와 무관하다.

### 2-5. 확인하지 못한 것

- 구글이 실제로 어느 항목을 문제 삼았는지
- 공개 글 14편이라는 분량이 단독으로 거절 사유가 되는지

분량 기준은 공식 문서에 없다. 아래 후기 사례는 참고일 뿐이다.

## 3. 다른 사이트에 쓸 체크리스트

### A. 색인 위생 (이번 사례의 핵심)

- [ ] 서치콘솔에서 **색인 생성됨 개수와 sitemap URL 개수를 비교**한다. 색인이 더 많으면 무엇이 추가로 색인됐는지 목록을 연다.
- [ ] 글이 1~2편뿐인 자동 생성 아카이브(태그, 연도, 작성자, 페이지네이션)가 색인되고 있는지 본다.
- [ ] 얇은 아카이브는 `noindex`와 sitemap 제외를 함께 건다. 둘 중 하나만 하면 부족하다.
- [ ] noindex 배포 뒤 **서치콘솔에서 해당 URL의 마지막 크롤링 날짜**를 확인한다. 배포일보다 이전이면 아직 반영되지 않은 것이다.
- [ ] 색인 숫자가 의도한 값으로 내려간 뒤에 신청한다.

재크롤링을 앞당기는 방법은 두 가지다.

1. URL 검사에서 개별 색인 요청. 하루 할당량이 적어 수십 개면 며칠 걸린다.
2. 삭제 도구에서 접두사 일괄 임시 삭제. 한 번에 되지만 접두사가 정상 페이지까지 잡지 않는지 확인해야 한다.

### B. 사이트 정합성

- [ ] 소개(About) 페이지가 실제 콘텐츠와 일치하는가. **템플릿 기본 문구가 남아 있지 않은가.**
- [ ] 없는 기능을 안내하고 있지 않은가 (댓글, 문의 양식, 뉴스레터, 검색)
- [ ] 홈의 사이트 설명과 소개 페이지의 주제 서술이 서로 어긋나지 않는가
- [ ] 플레이스홀더가 남아 있지 않은가 (`G-XXXXXXXXXX`, `YOUR_REPO_ID`, `lorem ipsum`, `example.com`)
- [ ] "설정해주세요" 같은 제작 중 표시가 프로덕션에 노출되지 않는가

플레이스홀더는 아래 한 줄로 훑을 수 있다.

```bash
grep -rniE 'YOUR_|XXXXX|lorem ipsum|example\.com|TODO' dist/ | grep -v '\.js:'
```

### C. 탐색 구조

- [ ] 카테고리가 있는가. 태그만으로는 주제 구조가 드러나지 않는다.
- [ ] **각 카테고리에 글이 3편 이상 있는가.** 1편짜리 카테고리는 얇은 태그 페이지를 반복하는 것이다.
- [ ] 카테고리 페이지에 목록 말고 **소개 문단**이 있는가. 목록만 있으면 그것도 얇은 페이지다.
- [ ] 브레드크럼과 BreadcrumbList 구조화 데이터가 있는가
- [ ] 헤더 메뉴만 봐도 사이트 주제가 보이는가

### D. 신뢰 요소

- [ ] 개인정보처리방침 (애드센스 필수)
- [ ] 문의 페이지. **실제로 동작하는 연락 수단만** 적는다. 정적 사이트면 양식 대신 이메일을 쓰고, 양식이 없는 이유를 밝힌다.
- [ ] 운영자 정보가 글 페이지에서도 보이는가 (바이라인, 하단 소개 박스)
- [ ] Article 또는 BlogPosting 구조화 데이터에 author와 publisher가 있는가
- [ ] 운영자 이름이 페이지마다 다르지 않은가 (단일 출처로 관리)

### E. 접근성

- [ ] 구글 크롤러 세 종류로 200이 나오는가

```bash
curl -s -o /dev/null -w "%{http_code}\n" -A "Googlebot" https://example.com/
curl -s -o /dev/null -w "%{http_code}\n" -A "Mediapartners-Google" https://example.com/
curl -s -o /dev/null -w "%{http_code}\n" -A "AdsBot-Google" https://example.com/
```

- [ ] robots.txt에서 위 셋이 차단되지 않았는가
- [ ] ads.txt에 실제 게시자 ID가 들어갔는가
- [ ] www와 apex가 모두 응답하고, canonical이 한쪽을 가리키는가

### F. 콘텐츠

- [ ] 글이 몇 편인가. 공식 기준은 없다. 아래 후기 사례가 참고가 된다.
- [ ] AI로 대량 생성한 글이 섞여 있지 않은가. 거절 사유로 가장 많이 지목된다.
- [ ] 한 주제를 여러 편으로 쪼갠 시리즈가 전체의 절반을 넘지 않는가. 목록만 보면 비슷한 글의 반복으로 보인다.

## 4. 참고 자료 평가

거절 후기 글을 여럿 봤다. 자료마다 신뢰도가 크게 달랐다.

| 자료 | 쓸모 있었던 것 | 걸러야 했던 것 |
|---|---|---|
| henrypress "저품질 콘텐츠 해결" | 거절 원인을 고유 콘텐츠 부족과 사이트 구조 혼란 두 축으로 정리. 카테고리 명확화 조언 | 구체 수치 없음 |
| lemonvita 재심사 합격 후기 | 실제 사례. 40편에서 거절, 맞춤법 교정과 이미지 alt 추가, **미색인 URL 색인 요청**, 30편 추가 후 승인 | 글 길이, 필수 페이지 정보 없음 |
| 유튜브 "사이트 다운, 중복계정" | 크롤러 접근과 중복 계정이라는 각도를 알려줌 | 본문 확인 실패 |
| 노션 "애드센스 승인용 프롬프트" | 신뢰 페이지 목록, 카테고리 페이지를 색인 가능하게 하되 소개문을 넣으라는 조언 | **신규 사이트 생성용**. 발행일을 최근으로 꾸미라는 조항과 AI로 글 15편 생성 조항은 쓰면 안 된다 |
| azaclub "승인 팁" | 거의 없음 | 승인 대행 홍보 글. "1,500~1,800자 엄수", "단 하나의 카테고리만", "반드시 크롬으로 신청" 모두 근거 없음 |

정리하면 이렇다.

- **서치콘솔 실측이 후기 글 열 개보다 낫다.** 이번 원인도 후기가 아니라 색인 보고서에서 나왔다.
- 후기 중에서는 **본인 사례와 수치를 밝힌 글**만 참고할 값이 있다.
- "필승 공식", "승인 대행" 류는 근거 없는 수치를 단언한다. 특히 글자 수 제한은 긴 글이 강점인 사이트에 해롭다.

## 5. meeemo.net에 적용한 수정

브랜치 `worktree-fix-about-page`, 커밋 3개다.

### 커밋 1. 소개 페이지를 실제 사이트 내용에 맞게 정리

| 삭제 | 이유 |
|---|---|
| "각 글의 댓글로 남겨주세요" | 댓글 기능 미작동. 없는 연락 수단 안내 |
| "일상: 일상적인 이야기와 생각" | 해당 글 0편 |
| "기록: 읽은 책, 본 영화" | 해당 글 0편 |
| "개인적인 이야기와 기술적인 내용을 함께" | 공개 글 전부 기술글 |

다루는 주제를 실제 태그 기준으로 다시 썼다. meta description도 "그나저나 블로그 소개"라는
빈 문장에서 실제 주제를 담은 문장으로 교체했다.

"가끔은 그 밖의 관심사도 적습니다" 한 줄을 남겨, 나중에 주제를 넓힐 때 문서를 다시 고치지
않아도 되게 했다. 축으로 선언하지는 않되 문은 열어두는 방식이다.

웹 개발 관련 글 4편에 `웹개발` 태그를 추가했다.

### 커밋 2. 카테고리 도입

얇은 태그 페이지 40개를 noindex로 막고 나니 색인되는 탐색용 구조 페이지가 `/blog/`
하나만 남았다. 소개 문단이 있는 카테고리 페이지로 그 자리를 메웠다.

| 카테고리 | 글 수 | 내용 |
|---|---|---|
| 데이터베이스 | 8 | 정규화 6편, IN vs EXISTS, 버스 정류장 LRS |
| 백엔드와 API | 4 | JPA 2편, Spring 테스트 OOM, Jackson null |
| 개발 도구 | 2 | 프롬프트 캐싱, Kotlin LSP |

글이 한두 편뿐인 카테고리를 만들지 않으려고 공간 데이터를 따로 빼지 않고 데이터베이스에
넣었다.

구현에서 중요한 부분이다.

- `src/consts.ts`의 `CATEGORIES`가 단일 출처다. slug, 이름, meta description, 본문 소개
  문단을 함께 관리한다.
- 태그 페이지와 달리 카테고리 페이지는 색인 대상이다. **각 카테고리에 소개 문단을 필수로
  두어** 목록만 있는 얇은 페이지가 되지 않게 했다.
- 스키마에서 `category`는 초안을 위해 optional이지만, 공개 글에 누락되면
  `/categories/` 빌드가 에러로 막는다. 실수로 분류를 빼먹을 수 없다.

```ts
const uncategorized = posts.filter((post) => !post.data.category);
if (uncategorized.length > 0) {
  throw new Error(`카테고리가 없는 공개 글이 있습니다: ...`);
}
```

### 커밋 3. 문의 페이지, 브레드크럼, 운영자 소개 박스

- `/contact/` 신설. 이메일과 GitHub 두 가지만 안내한다. **정적 사이트라 문의 양식을 두면
  내용이 전달되지 않으므로, 양식 대신 그 사실을 명시했다.** 답변 시점도 약속하지 않는다.
- 브레드크럼을 글, 카테고리, 문의 페이지에 넣고 BreadcrumbList 구조화 데이터를 함께 넣었다.
  글은 홈 > 카테고리 > 해당 카테고리 > 글 순서다.
- `src/consts.ts`에 `AUTHOR` 단일 출처를 두었다. 바이라인, 구조화 데이터의 author와
  publisher, 하단 소개 박스, 문의 페이지가 모두 여기를 참조한다. 이전에는 레이아웃에
  이름이 하드코딩되어 있었다.
- `AuthorBox` 컴포넌트를 만들어 글 하단에 붙였다.

검증 결과다. 빌드 65페이지 성공, 각 페이지 h1 1개, 카테고리 페이지 noindex 없음,

## 6. 아직 하지 않은 것

- **태그 페이지 색인 제거를 앞당길지 결정.** 자연 재크롤링을 기다릴지, 색인 요청이나 삭제
  도구를 쓸지.
- **글 수 늘리기.** 태그 26개가 색인에서 빠지면 색인이 19개로 줄어든다. 그것대로 얇다.
  초안 중 분량이 되는 것들을 게시하는 편이 비용이 가장 싸다.
- **애널리틱스 활성화.** GA4와 Cloudflare Analytics 둘 다 주석 처리 상태라 트래픽을 확인할
  수단이 없다. 재신청 판단 근거가 없다는 뜻이다.
- **Giscus 설정.** 지금은 소개 페이지에서 댓글 언급만 뺀 상태다. 실제로 붙이면 문장을
  되살린다.
- **이용약관과 면책고지.** 애드센스 필수 요건은 개인정보처리방침이다. 광고를 붙이는 사이트에
  있으면 좋다는 의견이 있어 판단이 필요하다.
해결됨(2026-08-18): `claude-code-kotlin-lsp-gradle-subdirectory` 글이 라이브에는 있는데
git에 없었다. 배포 직전에 발견해 커밋했다. 그대로 배포했으면 구글에 색인된 URL이 404가
될 뻔했다. **배포 전에 라이브 sitemap과 새 빌드 sitemap을 비교해 사라지는 URL이 없는지
확인하는 습관이 필요하다.**

```bash
curl -s https://example.com/sitemap-0.xml | grep -o '<loc>[^<]*' | sed 's/<loc>//' | sort > /tmp/live.txt
grep -o '<loc>[^<]*' dist/sitemap-0.xml | sed 's/<loc>//' | sort > /tmp/new.txt
comm -23 /tmp/live.txt /tmp/new.txt   # 출력이 있으면 그 URL이 사라진다
```
