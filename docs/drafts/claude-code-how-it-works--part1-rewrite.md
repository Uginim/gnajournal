Claude Code에 프롬프트를 한 번 입력해도 모델 요청은 한 번으로 끝나지 않습니다. Claude가 파일을 읽겠다고 응답하면 Claude Code가 파일을 읽고, 그 결과를 붙여 다시 모델을 호출합니다. 테스트 실행, 오류 확인, 코드 수정, 검증도 같은 왕복을 반복합니다.

이 구조를 알면 짧은 프롬프트 하나로도 작업 시간이 길어지는 이유, 읽은 파일과 명령 출력이 세션에 계속 남는 이유, 스킬·플러그인·서브에이전트가 컨텍스트에 미치는 영향이 연결됩니다. 이 글에서는 Claude Code가 요청을 만들고 작업을 진행하는 과정까지 다룹니다. 그렇게 만들어진 요청을 서버가 어떻게 캐싱하는지는 [다음 글](/blog/claude-code-tokens-and-prompt-caching/)에서 이어집니다.

> 2026년 7월 기준입니다. Claude Code는 자주 업데이트됩니다. 이 글과 현재 공식 문서가 다르면 공식 문서 쪽이 맞습니다.

## 요약

- Claude Code와 Claude 모델은 같은 것이 아닙니다. 모델이 다음 행동을 결정하면 Claude Code가 로컬에서 툴을 실행합니다.
- 사용자의 입력 한 번은 여러 모델 요청을 만듭니다. 툴을 사용할 때마다 결과를 추가한 새 요청이 나갑니다.
- 모델은 요청 사이의 상태를 기억하지 않습니다. Claude Code가 로컬 세션 기록을 바탕으로 그때까지의 컨텍스트를 다시 조립해 보냅니다.
- 저장소의 모든 파일이 자동으로 들어가지는 않습니다. 파일 내용과 스킬 본문은 필요할 때 읽거나 호출한 뒤 컨텍스트에 추가됩니다.
- 메시지, Claude의 응답, 툴 결과가 쌓이므로 같은 작업을 계속해도 요청은 점점 커집니다.

## Claude Code와 Claude 모델은 역할이 다름

Claude 모델은 파일을 직접 열거나 셸 명령을 실행하지 못합니다. 입력을 받아 텍스트나 `tool_use` 블록으로 다음 행동을 응답할 뿐입니다. 실제로 Read, Edit, Bash, Grep 같은 내장 툴을 실행하고 결과를 모델에게 돌려주는 주체는 로컬에서 실행 중인 Claude Code입니다. MCP 서버가 제공하는 툴도 같은 방식으로 중개됩니다.

따라서 Claude Code의 작업에는 두 종류의 실행이 번갈아 나타납니다.

1. Claude Code가 현재 컨텍스트를 모델에게 보냅니다.
2. 모델이 답변하거나 사용할 툴을 선택합니다.
3. 툴을 선택했다면 Claude Code가 로컬 또는 MCP 서버에서 실행합니다.
4. Claude Code가 실행 결과를 컨텍스트에 추가해 모델을 다시 호출합니다.
5. 모델이 작업 완료를 응답할 때까지 반복합니다.

모델은 무엇을 할지 결정하고, Claude Code는 그 결정을 외부 환경에서 실행하는 구조입니다. 일반 채팅과 달리 한 번의 입력이 파일 탐색부터 수정과 검증까지 이어질 수 있는 이유도 여기에 있습니다.

## 입력 한 번이 여러 요청을 만듦

공식 문서의 예시는 "실패하는 테스트를 고쳐줘"라는 입력이 어떻게 처리되는지 보여줍니다. Claude는 테스트를 실행하고, 오류 출력을 읽고, 관련 소스를 검색하고, 파일을 읽고, 수정한 뒤 테스트를 다시 실행합니다. 각 단계의 결과를 알아야 다음 행동을 정할 수 있으므로 모델 요청이 단계마다 새로 발생합니다.

![Claude Code의 에이전트 루프를 나타낸 공식 문서 도식. 사용자 프롬프트에서 시작해 컨텍스트 수집, 실행, 결과 검증을 반복하고 완료로 끝나며, 사용자가 중간에 끼어들어 방향을 바꾸거나 컨텍스트를 더할 수 있음을 보여준다](../../assets/claude-docs-agentic-loop.png)

> 에이전트 루프. 한 번의 프롬프트가 컨텍스트 수집, 실행, 검증을 반복합니다. 출처: [Claude Code 공식 문서, How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)

![사용자 입력 한 번이 요청 1, 2, 3 여러 개의 API 요청으로 이어지고 각 요청이 Bash와 Read 같은 툴 호출을 하며 그 결과가 다음 요청에 누적되는 구조를 나타낸 도식](../../assets/prompt-cache-agent-loop.svg)

사용자 입장에서는 입력 한 번이지만 서버 입장에서는 여러 요청입니다. 툴 호출이 많을수록 요청 횟수가 늘고, 각 툴 결과가 다음 요청의 판단 재료가 됩니다. Claude가 명령 하나를 오래 실행하고 있는 동안에는 모델이 계속 생각하는 것이 아니라, Claude Code가 명령이 끝나기를 기다리는 구간일 수도 있습니다.

반대로 서로 의존하지 않는 툴을 한꺼번에 호출하면 여러 결과를 모아 다음 모델 요청 한 번에 전달할 수 있습니다. 에이전트 루프의 길이는 사용자 메시지 수가 아니라, 다음 결정을 내리기 위해 몇 번의 모델 판단과 툴 실행이 필요한지에 가깝습니다.

## 모델은 이전 요청을 기억하지 못함

모델은 요청과 요청 사이에 세션 상태를 보관해 두고 이어서 읽지 않습니다. 이전 대화를 기억하는 것처럼 보이는 이유는 Claude Code가 그때까지의 대화와 작업 결과를 다음 요청에 다시 포함하기 때문입니다.

대화의 모든 메시지와 툴 결과는 로컬의 `~/.claude/projects/` 아래 JSONL 파일에 저장됩니다. JSONL은 JSON 객체를 한 줄에 하나씩 쌓는 텍스트 형식입니다. 프로젝트 경로의 `/`를 `-`로 바꾼 디렉토리 아래에 세션 ID별 파일이 생깁니다. Claude Code는 이 기록과 세션 시작 시 읽어 둔 설정을 조합해 요청을 만듭니다.

그래서 세션을 다시 열 수 있습니다. 서버에 대화 원본이 계속 붙어 있어서가 아니라, 로컬 기록으로 요청을 다시 구성할 수 있기 때문입니다. 캐시가 만료되어도 대화가 사라지지 않는 이유도 같습니다. 캐시는 계산 결과이고, 대화의 원본은 로컬 세션 기록입니다.

## 컨텍스트에는 무엇이 들어가나?

**컨텍스트**는 한 번의 모델 요청에 포함되는 입력 전체입니다. Claude Code의 동작 지시, 사용할 수 있는 툴, CLAUDE.md 같은 프로젝트 지침, 지금까지의 메시지와 툴 결과, 방금 입력한 내용이 함께 들어갑니다. 이 입력이 커질 수 있는 최대치가 **컨텍스트 윈도우**입니다.

저장소에 존재한다고 해서 모든 파일이 자동으로 컨텍스트에 들어가는 것은 아닙니다. 무엇이 언제 들어오는지를 나누면 다음과 같습니다.

| 내용 | 컨텍스트에 들어오는 시점 |
| --- | --- |
| Claude Code의 핵심 지시와 내장 툴 정의 | 세션 시작 |
| 유저·프로젝트 CLAUDE.md와 auto memory | 세션 시작 |
| 연결된 MCP 서버의 툴 정의 | 세션 시작 또는 tool search를 통한 지연 로딩 |
| 사용자 메시지와 Claude 응답 | 대화가 진행될 때마다 |
| 파일 내용 | Claude가 Read 등으로 읽은 뒤 |
| 셸 명령의 결과 | Claude Code가 명령을 실행한 뒤 |
| 스킬 본문과 슬래시 커맨드 | 호출할 때 |
| 하위 디렉토리의 CLAUDE.md와 경로 규칙 | 해당 경로의 파일을 처음 다룰 때 |

호출하지 않은 스킬의 본문, 읽지 않은 저장소 파일, 이전 세션의 대화는 현재 컨텍스트에 들어가지 않습니다. 스크립트를 실행해도 스크립트 코드가 자동으로 들어가는 것은 아니며 출력만 툴 결과로 추가됩니다.

공식 컨텍스트 윈도우 시뮬레이터에서는 사용자가 입력하기 전부터 시스템 프롬프트, auto memory, 환경 정보, MCP 툴, 스킬 설명, 유저·프로젝트 CLAUDE.md가 로드된 모습을 볼 수 있습니다. 문서의 대표 예시는 시작점만 약 7.8K 토큰입니다.

![Claude Code 공식 문서의 컨텍스트 윈도우 시뮬레이터 화면. 사용자가 입력하기 전에 이미 시스템 프롬프트 4.2K, 자동 메모리 680, 환경 정보 280, MCP 툴 120, 스킬 설명 450, 유저 CLAUDE.md 320, 프로젝트 CLAUDE.md 1.8K가 로드되어 약 7.8K 토큰이 쌓여 있는 모습](../../assets/claude-docs-context-before-typing.png)

## 응답도 다음 요청의 입력이 됨

컨텍스트에는 Claude 자신의 응답도 들어갑니다. 요청 N에서 출력한 답변이나 툴 호출은 요청 N+1부터 대화 기록의 일부가 됩니다. 툴이 돌려준 결과도 같은 위치에 쌓입니다.

![요청 N에서 Claude가 만든 응답이 요청 N+1에서 입력의 일부가 되는 구조를 나타낸 도식](../../assets/prompt-cache-output-becomes-input.svg)

이 때문에 긴 답변과 큰 툴 출력은 그 순간에만 자리를 차지하지 않습니다. 이후 요청마다 다시 포함됩니다. 빌드 로그 수천 줄을 그대로 읽히거나 큰 파일 여러 개를 통째로 열면, 그 내용은 이후의 모든 판단에 따라붙습니다.

컨텍스트를 크게 만드는 주된 원인은 보통 사용자 프롬프트보다 툴 출력입니다. 로그나 스택트레이스는 관련 구간만 전달하고, 큰 파일은 통째로 붙여넣기보다 경로를 알려 Claude가 필요한 부분을 찾게 하는 편이 낫습니다. `@` 프리픽스는 파일 전체와 CLAUDE.md 트리까지 주입하므로, 내용 전체가 필요한 것이 아니라면 경로만 적는 방법과 구분해야 합니다.

## 스킬은 단계별로 로드됨

스킬은 설치된 내용을 처음부터 전부 넣지 않습니다. 공식 문서가 progressive disclosure라고 부르는 방식으로 필요한 단계에서 나눠 로드합니다.

| 단계 | 들어오는 내용 | 시점 |
| --- | --- | --- |
| 1 | YAML frontmatter의 name과 description | 세션 시작 |
| 2 | SKILL.md 본문 | 스킬 호출 |
| 3 | 스킬에 포함된 참조 파일 | Claude가 해당 파일을 읽을 때 |

설치된 모든 스킬의 이름과 설명은 Claude가 어떤 스킬을 사용할지 판단할 수 있도록 미리 제공됩니다. 본문은 실제로 호출한 스킬만 대화에 추가됩니다. 스킬을 많이 설치하면 설명의 합계는 시작 컨텍스트에 영향을 주지만, 모든 SKILL.md 본문이 한꺼번에 들어가는 것은 아닙니다.

같은 스킬을 다시 호출했을 때 렌더링된 내용이 이미 들어온 것과 같으면, Claude Code는 본문을 다시 넣지 않고 이미 로드되었다는 짧은 노트만 추가합니다. 인자나 동적 컨텍스트가 달라 렌더링 결과가 바뀌면 새 본문을 대화 끝에 추가합니다.

## 플러그인은 하나의 거대한 프롬프트가 아님

플러그인은 스킬, MCP 서버, 커맨드, 훅 같은 확장을 묶어 설치하는 포장 단위입니다. 플러그인 전체가 하나의 텍스트로 컨텍스트에 들어가는 것이 아니라, 설치 후 각 구성요소가 자기 방식대로 작동합니다.

| 구성요소 | 동작 방식 |
| --- | --- |
| MCP 서버 | 제공하는 툴의 정의가 모델에 전달되고, 호출은 Claude Code가 중개 |
| 스킬 | 설명은 시작 시, 본문은 호출 시 로드 |
| 슬래시 커맨드 | 호출한 내용을 대화에 추가 |
| 서브에이전트 | 별도 컨텍스트에서 작업하고 결과를 부모 대화에 반환 |
| 훅 | 정해진 시점에 Claude Code가 직접 실행 |
| LSP 서버 | Claude Code에 코드 탐색 정보를 제공 |

특히 훅은 프롬프트 지시가 아닙니다. Claude가 내용을 읽고 따를지 판단하는 것이 아니라, Claude Code가 설정된 이벤트에 맞춰 로컬 명령을 실행합니다. 실행 결과를 모델에게 전달하도록 구성했다면 그 결과만 이후 컨텍스트에 나타납니다.

## 서브에이전트는 별도 컨텍스트에서 작업함

서브에이전트는 부모 대화의 전체 컨텍스트를 그대로 복제해 이어가는 방식이 아닙니다. 자기 시스템 프롬프트와 툴셋으로 별도 컨텍스트를 시작하고, 작업에 필요한 지시를 받은 뒤 결과를 부모에게 돌려줍니다.

그래서 코드베이스 전체 탐색이나 많은 파일을 읽는 조사를 서브에이전트에 맡기면, 그 과정의 모든 파일 내용과 툴 출력이 부모 대화에 쌓이지 않습니다. 부모에는 서브에이전트를 호출한 기록과 최종 결과가 남습니다. 대신 서브에이전트도 별도의 모델 요청을 사용하므로 작업량 자체가 없어지는 것은 아닙니다. 부모 컨텍스트와 탐색 컨텍스트를 분리하는 것이 핵심입니다.

## 세션이 길어지면 요청도 커짐

Claude Code는 요청마다 그때까지 쌓인 컨텍스트를 다시 조립해 보냅니다. 200K 컨텍스트 윈도우가 있다고 항상 200K를 보내는 것은 아닙니다. 현재 30K가 쌓였다면 약 30K가 전송되고, 작업이 진행되어 100K가 쌓이면 다음 요청도 그만큼 커집니다.

컨텍스트 윈도우가 가득 차기 전에도 큰 컨텍스트는 영향을 줍니다. 이후의 모든 요청이 커지고, 모델이 현재 작업에 필요한 정보와 오래된 정보를 함께 다뤄야 합니다. 그래서 Claude Code에는 서로 다른 목적의 정리 수단이 있습니다.

- `/clear`는 기존 대화를 비우고 새 컨텍스트로 시작합니다.
- `/compact`는 기존 대화를 요약으로 대체해 공간을 확보합니다.
- `/rewind`는 대화를 이전 시점으로 되돌립니다.
- 서브에이전트는 무거운 탐색 과정을 부모 컨텍스트 밖으로 분리합니다.

어느 방법이 비용 면에서 유리한지는 프롬프트 캐싱과 연결됩니다. `/compact`는 요약을 새 대화 기록으로 만들고, `/rewind`는 과거에 실제로 존재했던 기록으로 돌아갑니다. 이 차이를 포함해 서버가 반복 입력을 재사용하는 원리는 [Claude Code 프롬프트 캐싱: 토큰과 사용량이 달라지는 이유](/blog/claude-code-tokens-and-prompt-caching/)에서 이어서 설명합니다.

## 용어 정리

| 용어 | 뜻 |
| --- | --- |
| Claude 모델 | 입력을 바탕으로 답변이나 툴 사용 요청을 생성하는 모델 |
| Claude Code | 모델 요청과 로컬 툴 실행을 연결하고 세션을 관리하는 프로그램 |
| 에이전트 루프 | 모델 판단, 툴 실행, 결과 전달, 검증을 반복하는 과정 |
| 컨텍스트 | 한 번의 모델 요청에 포함되는 입력 전체 |
| 컨텍스트 윈도우 | 컨텍스트가 커질 수 있는 최댓값 |
| tool use | 모델이 Claude Code에 특정 툴 실행을 요청하는 응답 |
| tool result | Claude Code가 툴을 실행한 뒤 모델에 돌려주는 결과 |
| JSONL | JSON 객체를 한 줄에 하나씩 기록하는 텍스트 형식 |
