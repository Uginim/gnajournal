# 블로그 글쓰기 프로세스

그나저나 메모 블로그 글은 아래 순서로 쓴다. 특히 두 가지는 반드시 지킨다.

- **주장을 한 문장으로 먼저 확정한다.** 주장이 정해지기 전에는 본문을 쓰지 않는다.
- **도입부는 혼자 확정하지 않는다.** 항상 사용자와 상의해 맞춘 뒤 쓴다.

## 순서

### 1. 소재 확정
- `docs/blog-candidates.md`나 gist, 노트에서 고른다.
- IP 점검: 사내 식별자, 티켓번호, 타사 제품명, 그리고 특정 동료를 지목하거나 깎는 내용이 없는지 본다. 사람 이야기는 무인칭으로 일반화한다.

### 2. 주장 한 문장 확정 (사용자와 합의)
- "이 글로 무엇을 주장하는가"를 한 문장으로 못박는다. 예: "EXISTS는 억울하다. 느린 건 문법이 아니라 쿼리 구조였다."
- 이 문장이 글의 축이다. 제목, 도입부, 결론이 모두 이 한 문장을 향한다.
- 주장이 서기 전에는 다음 단계로 가지 않는다.

### 3. 골자(목차) 합의
- 주장을 뒷받침하는 섹션 흐름을 목차로 잡고 확인받는다. 예: 사건, 오진 바로잡기, 원리, 실측, 판단, 결론.
- `toc-flow-review` 스킬을 참고한다.

### 4. 근거 확보
- 필요하면 로컬 재현과 실측을 한다. 벽시계 시간보다 결정적 지표(Handler 카운터, 파싱 횟수 등)를 우선한다.
- 1차 출처 인용은 원문 대조 후에만 축자 인용한다. 못 하면 의역임을 드러내거나 뺀다.

### 5. 초안 작성
- `blog-user-voice`, `blog-formal-tone`, `blog-writing-short-sentences` 결로 처음부터 쓴다.
- 자기 증명조("직접 해봤다"), 필러와 신호등, 비유, 과장을 넣지 않는다.

### 6. 도입부는 사용자와 상의
- 도입부를 단독으로 확정하지 않는다. 주장과 사건 프레임을 사용자와 맞춘 뒤 쓴다.
- 통념 반박 예고("~같은 격언이 있는데 틀렸다") 상투구를 피한다. 사건이나 틀린 짐작을 바로 제시한다.

### 7. 말투 검사
- `blog-tone-check` 스킬을 처음부터 끝까지 돌린다. 부분 grep으로 대충 넘기지 않는다.
- 저장 훅 통과를 확인한다.

### 8. 사실과 IP 최종 점검
- 수치, 인용, 기능이 검증됐는지 본다. 미검증은 미래형으로 쓰거나 뺀다.
- 동료 지목, 사내 식별자, 타사 제품명이 없는지 다시 확인한다.

### 9. 빌드와 로컬 확인, 사용자 리뷰, 배포
- `npm run build`로 확인하고 dev 서버로 본다.
- 게시 전 사용자 리뷰를 받는다. 배포는 사용자 승인 후에 한다.
