집계 쿼리를 돌리던 중에 ORA-08103 오류를 만난 적이 있습니다.

```
ORA-08103: object no longer exists
```

오류 메시지는 "객체가 더 이상 존재하지 않는다"고 하는데, 정작 그 테이블은 멀쩡히 존재합니다. `SELECT * FROM ...`을 다시 실행하면 잘 나옵니다. 그런데 특정 집계 쿼리에서만 이 오류가 납니다. 그 원인을 이해하고 대응한 과정을 정리했습니다.

## 오류의 실제 의미

ORA-08103은 이름 때문에 오해하기 쉽습니다. "객체가 없다"가 아니라, "쿼리가 읽으려던 순간에 대상 세그먼트(블록)의 정체성이 쿼리 시작 시점과 달라졌다"는 뜻에 가깝습니다.

Oracle은 쿼리를 실행할 때 대상 객체를 이름이 아니라 내부 식별자인 `DATA_OBJECT_ID`로 추적합니다. 쿼리가 실행되는 도중에 그 객체의 `DATA_OBJECT_ID`가 바뀌거나, 읽으려던 블록이 더 이상 그 객체의 것이 아니게 되면, Oracle은 자기가 읽으려던 객체가 아니라고 판단하고 ORA-08103을 냅니다.

즉 테이블 이름은 그대로여도 세그먼트 실체가 교체되면 이 오류가 납니다. 그래서 존재하는데 없다고 하는 모순처럼 보이는 상황이 생깁니다.

## 흔한 원인

원인은 대체로 네 가지 중 하나입니다.

- **쿼리 실행 중 DDL이 끼어든 경우**: 가장 흔합니다. 긴 집계 쿼리가 도는 동안 대상 테이블에 `TRUNCATE`, `DROP` 후 재생성, `ALTER TABLE ... MOVE`, 파티션 조작, 인덱스 `REBUILD` 같은 작업이 들어오면 `DATA_OBJECT_ID`가 바뀝니다. `TRUNCATE`만 해도 세그먼트가 새로 할당되며 식별자가 갱신됩니다. 실행 중이던 쿼리는 옛 세그먼트를 찾다가 ORA-08103을 만납니다.
- **Global Temporary Table(GTT) 관련**: 세션이나 트랜잭션 단위로 데이터가 사라지는 임시 테이블을 다른 세션이나 다른 트랜잭션 시점에 참조하려 하면 발생할 수 있습니다.
- **물리적 스탠바이(Data Guard) 환경**: Active Data Guard 같은 읽기 전용 스탠바이에서 리포팅 쿼리를 돌릴 때, primary에서 넘어온 리두를 적용하는 과정과 스탠바이의 조회가 시점상 충돌하면 이 오류가 날 수 있습니다. primary에서의 DDL이나 공간 재구성이 스탠바이에 반영되는 타이밍 문제입니다.
- **블록 손상이나 delayed block cleanout 같은 물리적 이슈**: 드물게 인덱스나 테이블 블록의 물리적 정합성 문제로도 나타납니다.

## 어떤 객체가 문제인지 특정하기

먼저 무엇이 문제인지 특정해야 합니다. 오류가 난 세션의 트레이스 파일이나 알럿 로그에는 보통 문제의 `object#`이나 `data_object_id`가 남습니다. 그 값으로 실제 객체를 역추적합니다.

```sql
-- data_object_id로 실제 객체 찾기
SELECT owner, object_name, object_type, object_id, data_object_id
FROM   dba_objects
WHERE  data_object_id = &문제의_id;
```

문제 객체가 테이블인지 인덱스인지, 파티션인지에 따라 대응이 갈립니다.

## 대응

### 동시 DDL이 원인이면 운영 스케줄 분리

가장 근본적인 해결입니다. 긴 조회나 집계 쿼리가 도는 시간대에 해당 테이블을 `TRUNCATE`하거나 재적재하는 배치가 겹치지 않도록 스케줄을 분리합니다. 집계 중에 원본을 바꾸는 구조 자체가 문제의 원천인 경우가 많습니다. 실무에서는 이것이 핵심입니다.

### 인덱스가 의심되면 재생성

특정 인덱스를 타는 실행 계획에서만 오류가 난다면 인덱스 정합성을 의심하고 재빌드합니다.

```sql
ALTER INDEX 스키마.인덱스명 REBUILD;
-- 온라인 재빌드가 필요하면
ALTER INDEX 스키마.인덱스명 REBUILD ONLINE;
```

인덱스를 우회해서(예: 힌트로 풀스캔 유도) 쿼리가 정상 동작하는지 확인하면, 인덱스가 범인인지 빠르게 판별할 수 있습니다.

### 테이블 구조와 블록 검증

```sql
ANALYZE TABLE 스키마.테이블명 VALIDATE STRUCTURE CASCADE;
```

구조 검증에서 오류가 잡히면 블록 손상 가능성이 있으므로, DBA와 함께 복구 절차(백업 복원, `DBMS_REPAIR` 등)를 검토합니다.

### 통계 재수집과 커서 무효화

오래된 실행 계획이 이미 없어진 세그먼트를 가리키는 경우가 있어, 통계를 다시 모으고 관련 커서를 무효화하면 해소되기도 합니다.

```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS('스키마', '테이블명');
```

### 스탠바이 환경이면

리포팅을 Active Data Guard에서 돌리다 발생했다면, 문제 구간을 primary로 옮기거나 리커버리와 조회 타이밍이 겹치지 않도록 조정하는 방향을 DBA와 협의합니다.

## 정리

ORA-08103의 핵심은 이름은 그대로여도 실체가 바뀌었다는 것입니다. 그래서 디버깅의 출발점은 두 가지 질문입니다.

1. 이 쿼리가 도는 동안 대상 테이블에 `TRUNCATE`, 재적재, DDL이 끼어들지 않았는가?
2. 문제가 테이블인가 인덱스인가? (`data_object_id`로 특정)

제 경우는 집계 쿼리가 도는 사이 원본 테이블을 바꾸는 작업이 겹친 것이 원인이었고, 작업 순서를 분리하자 재현이 사라졌습니다. 물리적 손상까지 가는 경우는 드뭅니다. 오류 이름보다 누가 이 세그먼트를 건드렸는지를 먼저 추적하는 편이 빠릅니다.
